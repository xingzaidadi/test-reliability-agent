# AI 测试的"最后一公里":用例能生成,为什么进不了真实系统?

> 你见过多少"AI测试"的演示,最后停在了 demo?
> 它们能生成漂亮的用例,却跑不进你那个要签名、要 token、要 SSO 的真实系统。
> 这篇讲一个被严重低估的命题:**"能生成用例"和"能跑进真实业务系统"之间,隔着一条鸿沟**——以及我怎么用一段真实的排障,趟平了其中一段。

---

## 一、一个行业里没人愿意说的真相

打开任何"AI 自动化测试"的分享,90% 停在同一个地方:**生成用例,然后……就没有然后了。**

为什么?因为演示用的都是干净的、公开的、无鉴权的接口。而你真实要测的系统:

- 要**签名鉴权**(每个请求要按私有协议算签名)
- 要**token / cookie / SSO**(登录态怎么拿)
- 要**特定协议**(不是标准 REST,是公司自己的 网关/gRPC/私有封装)
- 要**测试数据**(查询得有数据,写操作得能回滚)

**AI 能写出语法完美的用例,但它跑不进这些系统。** 这就是"最后一公里"——从"用例文件"到"真正穿透业务接口"的距离。**这一公里,决定了 AI 测试是玩具还是工具。**

一套工程化控制原则反复强调一条原则:**机器可验证优于 AI 自述。** 放到这里就是:**用例只有真的发出去、真的拿到响应、真的断言通过,才算"测了"。跑不进去的用例,等于没测。**

---

## 二、我撞上的那堵墙:一直 500

我要测的某后端系统,用的是某企业级网关协议。我把 AI 生成的用例(结构完全正确)发出去:

```
HTTP 500  {"code": 50000000, "message": "服务内部异常"}
```

改参数、补字段、换 method——**还是 500。** 用例本身没问题,是它**根本没被系统接受**。

这就是最后一公里的墙:**用例对了,但它跨不过协议这道关。**

---

## 三、还原那道关:网关签名协议

排查发现,该网关协议要的不是裸 JSON,而是一套"签名 + 信封 + 编码"的封装。抽象成四步(不同网关细节不同,这里只讲思路):

```text
1. 用凭证 + 请求体算一个摘要签名(如 HMAC/MD5 一类)
2. 把签名和业务体一起塞进一个"信封"结构(header + body)
3. 对信封做一次编码(如 Base64)
4. 按网关要求的传输格式发出(如 form 表单字段)
```

> 注:具体签名算法与字段是各企业网关的内部约定,这里只抽象出通用步骤,不展开可复刻的公式。关键不是某一种签名,而是**"把签名这层脏活封装进执行器,让上层用例无感知"**这个设计。

把它内置进执行器,对上层用例**透明**——写用例的人不用懂签名,执行器自动签。再发:

```
HTTP 200 ✓  真实业务响应回来了
```

**从 500 到 200,跨过的就是这最后一公里的一段。**

---

## 四、跨过之后:真实的执行,才有真实的数据

一旦能真穿透,平台立刻能拿到普通 demo 拿不到的东西——真实执行数据:

```
TC_001 正向查询    PASS  http=200  115ms
TC_002 缺字段      PASS  http=200   89ms
TC_003 不存在      PASS  http=200   71ms
3/3 真跑通

性能基线(15次采样): p50=78ms / p95=104ms, 0错误
```

这些数字,mock 是给不了的。**真穿透,才有真数据;真数据,才有真判断。**

---

## 五、把"最后一公里"当成系统工程,而不是偶然

签名只是这条鸿沟的**一个切片**。完整的"最后一公里"是一套系统工程,我把它抽象成执行器要解决的几类问题:

| 关卡 | 怎么解 |
|---|---|
| 协议/签名 | 还原后内置,对用例透明(如 gateway_wrap) |
| 鉴权凭证 | 环境变量注入,不写死进用例 |
| 登录态(UI) | storage_state 复用,登录一次存下来 |
| 测试数据 | 只读优先;写操作要求可回滚 |

**关键设计思想**:这些"脏活"应该沉淀在执行器里,而不是暴露给用例。用例只描述"测什么",执行器负责"怎么真的发出去"。**这样 AI 生成的用例才能真正落地,而不是停在语法正确的 demo。**

---

## 六、复现

```bash
export TARGET_SYSTEM_BASE_URL="..."
export TARGET_SYSTEM_SECRET="..."   # 环境变量注入,不落文件
python cli/test_squad.py run-api --issue ISSUE-001    # 真发,含签名
```

签名逻辑在 `tools/api-runner/api_execution_tool.py` 的 `gateway_wrap`。换成你系统的协议即可。

---

## 七、诚实边界

- 我真跑通的是 API 链路(含 网关签名)。**UI 链路(要过 SSO)在本项目没跑通**——因为某后端系统是纯后端无 UI;浏览器自动化的真实经验在我另一个 RPA 项目里。
- 不同系统的"最后一公里"不同:网关 是签名,别的可能是 OAuth、mTLS、验证码。机制思路通用(内置到执行器),但每个系统要单独适配。

---

> **一句话**:AI 生成用例只是起点,能穿透真实系统的鉴权和协议,才是 AI 测试从玩具变工具的分界线。这最后一公里,是系统工程,不是运气。
