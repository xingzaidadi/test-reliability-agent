# 我给 AI 一句需求,没告诉它测哪个接口,它自己找到了

> 大部分"AI测试"是这么用的:你把接口文档喂给它,它生成用例。
> 但真实工作里,你手上先有的往往不是接口文档,是**一句需求**。
> 这篇讲:怎么让 AI 从"一句业务需求"出发,自己读懂代码、推导出该测哪些接口、设计出测试——以及为什么这一步,才是 AI 测试平台真正的"入口高度"。

---

## 一、大多数"AI测试"的起点,其实错了

你见过的 AI 测试 demo,几乎都是这个套路:

```
把 OpenAPI / 接口定义丢给 AI → AI 生成用例
```

问题是:**这个起点假设了"接口已经明确"。** 可现实是——需求评审刚开完,产品说"我们要支持按费用类型查价格",这时候哪来的接口文档?接口还没定,或者散落在几千行代码里。

真正的测试工作,起点是**需求**,不是接口。测试工程师要做的第一件事,是**把需求翻译成"该测什么"**——这一步叫可测性分析,是测试设计里最难、最体现专业度的环节。

如果 AI 测试平台只能从"接口"开始,它就只是个用例生成器;能从"需求"开始,它才是个测试平台。

**这也正是小米内部 AI 框架 VAF 的设计——它的流程从 P01 需求采集开始,接口只是需求流转到设计阶段的中间产物。** 我把这个思路搬到了测试上。

---

## 二、一个刻意的实验:我不告诉它接口

我写了一张需求单,**故意不写任何接口名**:

```markdown
# 需求单 REQ-001
需求:价格中心支持按费用类型查询采购价格。
传入采购组织+标的物+供应商+费用类型,拿到价格。
- 费用类型传错要报错
- 必填字段缺失要校验
- 查不到要友好提示

目标系统源码:.../isc-server-price
(需求方只描述业务,不指定接口——由测试Agent自己从源码分析)
```

然后把它交给平台。看它能不能自己找到该测的接口。

---

## 三、关键机制:源码驱动,不许"猜"

这里有个**反幻觉**的关键设计。如果直接问 AI "这个需求该测哪些接口",它会凭训练记忆瞎编一个 `/api/price/query` 之类**根本不存在**的接口——这就是幻觉,不可信。

VAF 的原则是:**反幻觉需要机制,不只是 Prompt。** 具体到这里:**必须让 AI 先读真实源码,再推导。**

所以我给 AI 的输入是"需求单 + 从源码扫出来的真实接口清单":


> 📸 **配图位置**:此处配一张 demo_requirement.py 输出的可测性分析JSON 的真实截图(运行命令后截屏)

```python
# 从 ApiX5Controller 真实源码提取的接口清单,连同枚举一起喂给AI
source_apis = (
    "源码里的X5接口清单:\n"
    "- /x5/api/pullPrice (拉取价格模型)\n"
    "- /x5/api/getPrice (获取价格)\n"
    "- /x5/api/getQty (查询数量)\n"
    "priceType枚举: MVAFee/sampleFee/.../COST"
)
# 需求 + 真实接口 → 让AI做可测性分析
task = Task(skill="analyze_requirement",
            payload={"requirement": requirement + source_apis})
```

**它推导的接口,必须是源码里真实存在的**——这是可信的前提。

## 四、它交出了什么(真实运行结果)

codex(GPT-5.5)跑了 43 秒,输出:

```json
{
  "requirement_summary": "支持按采购组织/标的物/供应商/费用类型查询采购价格...",
  "testability": "部分可测:核心查询/校验/枚举/未找到能覆盖;
                  但'有效价格模型'判定规则和性能要求缺量化标准,需确认",
  "derived_apis": [
    "/x5/api/pullPrice(拉取价格模型)",
    "/x5/api/getPrice(获取价格)"
  ],
  "test_points": [
    "传入合法参数能返回价格",
    "priceType非法值返回枚举校验错误",
    "必填字段缺失返回参数校验错误",
    "查不到时返回明确未找到提示,不应抛异常",
    "pullPrice与getPrice同条件返回一致性",  // ← 注意这条
    ... (共9个测试点)
  ],
  "p0_risks": ["费用类型枚举校验不严导致错误价格被返回", ...]
}
```

三个地方,让我确认这不是"模板套壳":

1. **它自己找到了接口**:需求单里我没写任何接口名,它从需求+源码关联出了 `pullPrice` 和 `getPrice`。
2. **它有可测性判断**:主动指出"性能要求缺量化标准,需确认"——这是**资深测试才有的意识**:不是所有需求都能直接测,有的得先让需求方把标准说清楚。
3. **它想到了跨接口用例**:"pullPrice 与 getPrice 结果一致性"——这种用例,只盯单个接口是想不到的,需要理解"这俩接口在业务上应该等价"。

---

## 五、为什么这一步是"入口高度"

对比一下两种平台:

| | 从接口出发 | 从需求出发(本文) |
|---|---|---|
| 输入 | 接口文档(得先有) | 一句业务需求 |
| AI做的事 | 把接口翻译成用例 | 读懂需求→关联代码→推导接口→设计测试 |
| 定位 | 用例生成器(工具) | 测试平台(能力) |

**从需求出发,意味着平台承担了"可测性分析"这个最能体现测试专业度的环节。** 接口测试反而降级成了下游的执行环节——这才是平台该有的样子。

---

## 六、复现

```bash
# 需求单 + 源码接口清单 → 可测性分析 → 测试设计(DAG串联)
python orchestrator/demo_requirement.py
```

需求单放 `outputs/runs/REQ-001/requirement.md`,换成你自己的需求即可。代码在 [GitHub](https://github.com/xingzaidadi/test-reliability-agent)。

---

## 七、诚实边界

- "从源码扫出接口清单"这一步,目前我是手工抓的注解喂进去;**让平台全自动扫Controller建清单**(context_load节点)还在接入中。也就是说,当前是"给需求+源码接口清单→推导",全自动的"给需求+源码路径→自己扫→推导"是下一步。
- 推导质量依赖源码信息的完整度:源码注解越全(如 `@HttpApiDoc`),推导越准。

---

> **一句话**:能从"接口"生成用例的,是工具;能从"需求"读懂该测什么的,才是平台。而让这一步可信的关键,是逼着 AI 读真实源码——不给它凭空想象的机会。
