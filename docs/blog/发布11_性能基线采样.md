# 功能全绿 ≠ 性能没问题:这个接口 p95 悄悄飙到了 382ms(偶发破 1 秒)

> 功能测试跑通了,但"这接口快不快"你心里有数吗?
> 这篇讲一个低成本高回报的能力:**复用已跑通的接口链路,顺手采个性能基线(p50/p95)**——
> 以及一个诚实的边界:这是**采样,不是压测**,别把两者搞混。

---

## 一、功能对了,不代表性能没问题

一个接口功能测试 PASS,只说明"结果对"。但它可能:
- 平时 80ms,p95 却飙到 382ms,某些请求偶发破 1 秒(max=1073ms)
- p50 很好看,p95 惨不忍睹(长尾)

这些光看功能测试发现不了。**你需要一个性能基线**——知道它正常多快、尾部多慢,才能在它变慢时察觉。

---

## 二、几乎零成本:复用功能测试的链路

关键设计:**性能采样不重写请求,复用功能测试的 `run_case`(含 网关签名)**,只是同一个用例连发 N 次,统计分布。

```python
def run_perf_case(case, n=15):
    samples = [run_case(case)["duration_ms"] for _ in range(n)]  # 连发N次
    ordered = sorted(samples)
    return {
        "p50": percentile(ordered, 50),
        "p95": percentile(ordered, 95),
        "max": max(ordered),
    }
```

功能测试已经把"怎么真发出去"解决了,性能采样白捡这个能力——**加几十行,多一项能力。**

---

## 三、真实基线(15次采样)

> 📸 配图位置:此处配一张 --perf 采样输出 p50/p95 的真实截图

```
[PERF] TC_001 正向查询 x15 ... p50=79.6ms  p95=114.8ms  max=136.8ms  err=0
[PERF] TC_002 缺字段   x15 ... p50=72.5ms  p95=382.4ms  max=1073ms   err=0
```

看 TC_002 那行——**p50 才 72ms,但 p95 飙到 382ms,max 破 1 秒。** 这个长尾,单跑一次功能测试根本发现不了,采样才暴露出来。**这就是基线的价值:让你看见平均值藏起来的尾部风险。**

---

## 四、诚实的边界:这是采样,不是压测

我必须把这条边界说死,否则就是误导:

| | 性能基线采样(本文) | 压测 |
|---|---|---|
| 方式 | 串行连发 N 次 | 高并发打流量 |
| 目的 | 摸响应时间分布 | 找系统极限/瓶颈 |
| 对环境 | 几乎无压力 | 真加压 |

**它回答"这接口平时多快、尾部多慢",不回答"能扛多少并发"。** 真要压测,得上专门框架(JMeter/Gatling)。结果文件里我也写死了这句:`"note": "单请求串行采样,非并发压测"`——**不夸大成压测。**

---

## 五、复现

```bash
python tools/api-runner/api_execution_tool.py \
    --issue ISSUE-001 --perf --samples 15 --priority P0
```

---

## 六、诚实边界

- 采样非压测(上面说透了)。
- 串行采样受本机网络波动影响,基线应在稳定网络下多次取。

---

> **一句话**:功能测试证明"对不对",性能基线证明"快不快、尾部稳不稳"。复用已有链路,几十行就多一项能力——但记得诚实标注:这是采样,不是压测。
