# 你的 AI 测试用例,可能正在制造"虚假的安全感"

> 我让 AI 给一个接口生成了测试用例,它信心满满地交了 4 条。
> 我写了个程序拿源码一算——**覆盖率 48%,漏了一半**。
> 这篇讲:为什么"AI 生成的测试"最危险的不是跑不起来,而是它让你以为测过了;以及我怎么用 200 行代码,把"测得全不全"从一句感觉,变成一个可验证的数字。

---

## 一、一个让我后背发凉的问题

现在用 AI 写测试用例已经很普遍了:把接口丢给 GPT,它唰唰给你生成一堆用例,看起来专业、分类齐全、还带断言。

但有天我盯着 AI 生成的用例,突然想到一个问题:

> **我怎么知道它没漏?**

它生成了 4 条。可能该有 10 条。那漏掉的 6 条——恰恰是线上会炸的那 6 条呢?

**这比"AI 不会写测试"可怕得多。** AI 不会写,你知道它不会,你会自己补。但 AI 写了、看着还挺全、你就放心上线了——**它给了你一种"测过了"的错觉。测试的本职是消除不确定性,而一个不可信的测试,是在制造不确定性,还伪装成确定性。**

这就是我说的**虚假的安全感**。而且它有个更尖锐的悖论:

> 测试这件事的灵魂是"不信任、要验证"。而我们现在,把它交给了一个最不该被无条件信任的东西——一个概率性的、会一本正经胡说八道的语言模型。

---

## 二、一个被验证过千百遍的元原则

这个问题不新。我在读小米内部两套 AI 控制框架(VAF/VCB)的设计时,看到一句话,一下击中了我:

> **AI 能力由模型决定,AI 可靠性由你构建的控制系统决定。**

模型再聪明,也只是"能力"变强;它会不会漏、会不会撒谎,是"可靠性"问题——**这不归模型管,归你的工程设计管。**

VAF/VCB 从 AI 编码里提炼了一条原则,我把它搬到 AI 测试上:

> **机器可验证,优于 AI 自述。**
> 不要问 AI"你测全了吗",它会说"测全了"(研究表明 LLM 对自己的自评普遍高估 15-20%)。要用一个它无法糊弄的外部机制,去算它到底测了多少。

那个"外部机制",就是这篇的主角。

---

## 三、把"全不全"变成一个数字:覆盖率反推

思路很简单,但很多人没做:**用被测系统的源码,当测试覆盖率的分母。**

被测接口(Java)的入参对象里,写着真相:

```java
public class PullPriceX5Req {
    @NotBlank(message = "采购组织编码不能为空")
    private String purchaseOrg;      // 必填
    @NotBlank(message = "采购标的物编码不能为空")
    private String objectCode;       // 必填
    @NotBlank(message = "供应商编码不能为空")
    private String vendorCode;       // 必填
    @NotBlank(message = "费用项类型不能为空")
    @EnumRange(strValues = {"MVAFee","sampleFee","ODMOwnedFee",
        "materialBSFee","commissionFee","materialFee","COST"})  // 枚举7个值
    private String priceType;
}
```

这段代码告诉我:**一份"充分"的用例,至少应该覆盖 4 个必填参数的缺失场景、7 个枚举值、以及每个接口。** 这就是分母。

于是我把这些抽成一份"分母清单":

```json
{
  "apis": ["/x5/api/pullPrice", "/x5/api/getPrice", "/x5/api/getQty"],
  "required_params": ["purchaseOrg", "objectCode", "vendorCode", "priceType"],
  "enums": { "priceType": ["MVAFee","sampleFee","...","COST"] },
  "error_codes": [400, 401, 3007]
}
```

然后写个分析器,拿 AI 生成的用例去比对这个分母(核心逻辑,约 200 行):

```python
def gate1_coverage(spec, cases):
    cases_text = json.dumps(cases, ensure_ascii=False)
    # 接口:每个接口是否至少1条用例
    api_missing = [a for a in spec["apis"] if a not in cases_text]
    # 枚举:每个枚举值是否被覆盖
    for field, values in spec["enums"].items():
        covered = [v for v in values if v in cases_text]
        # ... 算覆盖率
    # 错误码:期望的错误场景是否有用例
    ec_missing = [ec for ec in spec["error_codes"] if str(ec) not in cases_text]
    # 加权综合(接口40% 参数30% 枚举20% 错误码10%)
    return overall_pct, {"缺接口": api_missing, "缺错误码": ec_missing, ...}
```

跑一下真实结果:


> 📸 **配图位置**:此处配一张 coverage_analyzer 跑出48.1%的终端 的真实截图(运行命令后截屏)

```
[闸①覆盖率] 48.1%
[判定] 不充分-需补
[缺口] 缺接口用例: pullPrice, getQty(只测了getPrice)
       缺错误码用例: 401鉴权, 3007未找到
       缺测试维度: 枚举非法值
```

**48.1%。** AI 交的 4 条用例,只测了一个接口的正向路径,漏了另外两个接口、两类错误码、和所有枚举非法值。

如果没有这个数字,我就上线了。这就是虚假安全感被戳破的一刻。

## 四、光有一个数字还不够:四道闸

覆盖率反推解决了"漏接口/参数"。但"漏"有四种,一道闸堵不住:

| 漏的类型 | 例子 | 对策 |
|---|---|---|
| 漏接口/参数 | 某接口没用例 | **闸① 覆盖率反推**(源码当分母) |
| 漏测试维度 | 测了正向,忘了越权 | **闸② 维度清单**(固定维度扫一遍) |
| 漏"想不到的" | 刁钻组合场景 | **闸③ 对抗补全**(AI 拿着缺口清单补) |
| 漏"已知会坑的" | 这类系统历史栽过的坑 | **闸④ 缺陷模式比对** |

四道闸串成一条流水线,真实跑一遍:

```
[初测]        覆盖率48.1% | 维度85.7% | 判定"不充分"
[闸③对抗补全]  拿缺口清单驱动AI补2条 → 维度 85.7%→100%
[闸④缺陷模式]  71.4% | 高风险漏测:"假成功"模式未覆盖
[最终]        覆盖率48.1% | 维度100% | 缺陷模式71.4% | 判定"仍不充分"
```

注意最后一行——**流水线判定"仍不充分"。它没给我一个漂亮的 100%。**

这恰恰是我最得意的地方:**它诚实。** 它清楚告诉我还差 pullPrice/getQty 接口、401/3007 错误码、"假成功"模式没测。它不粉饰、不邀功——因为它是个机器,不是个想让你满意的 AI。

## 五、闸④ 有意思:让平台记住"已知会坑的"

闸①②③ 解决"结构上全不全",闸④ 解决"经验上有没有踩过的坑"。

我建了一个缺陷模式库,里面有通用模式,也有我这个项目**真实踩过的坑**:

```yaml
- id: DP001
  source: "本项目真实发现"
  name: "HTTP状态码与业务码不一致"
  desc: "参数错误时HTTP=200但业务header.code=400。只看HTTP码的监控会漏报。"
  severity: high
- id: DP002
  source: "本项目真实发现(RPA经验迁移)"
  name: "假成功:错误提示被当成功"
  desc: "服务端返回错误提示词但被判成功。断言必须校验真实业务状态。"
  severity: high
```

用例集跑一遍比对,它会告诉你:"你没覆盖'假成功'这个高危模式。" —— **把散落在老工程师脑子里的'踩坑记忆',变成一个平台能自动检查的资产。** 这也是 VAF/VCB 讲的"skill 复用":每个踩过的坑,变成全队都能受益的检查项。

## 六、回到那个悖论

开头我说,把测试交给不可信的 AI 是个悖论。现在我的答案是:

> **你不需要信任 AI。你需要的是一套让 AI 无法蒙混过关的验证机制。**

AI 生成用例——但我用源码算它覆盖率;AI 说测全了——但我用缺陷模式库查它漏没漏;AI 补全——但我拿机器算出的缺口清单指挥它补,补完再复算。

**AI 在这套系统里,不是一个被信任的专家,而是一个被持续验证的执行者。** 它可以很聪明,但它蒙不了这套闸。

这才是"AI 测试"该有的样子——不是"我让 AI 写测试所以我很先进",而是"**我构建了一套系统,让 AI 写的测试变得可信**"。前者是虚假安全感,后者是真安全感。差别就在这套你看不见、但一直在算的闸上。

## 七、你可以自己跑

代码开源在 [GitHub](https://github.com/xingzaidadi/test-reliability-agent)(脱敏版)。核心就 `tools/sufficiency/` 五个文件:

```bash
# 拿源码分母 + AI生成的用例,算覆盖率
python tools/sufficiency/coverage_analyzer.py --spec api_spec.json --cases api_cases.yaml
# 四闸完整流水线
python tools/sufficiency/sufficiency_pipeline.py --spec api_spec.json \
    --cases api_cases.yaml --patterns defect_patterns.yaml
```

把 `api_spec.json` 换成你自己系统的接口分母,就能算你的 AI 用例到底测了几成。

**我赌你第一次跑,数字不会好看。** 但那个不好看的数字,比之前那份"看着挺全"的用例,值钱得多。

---

> **一句话**:AI 能帮你写测试,但不能帮你保证测得全。保证充分性的,永远是你构建的验证系统——这套系统,才是测试开发在 AI 时代真正的护城河。
