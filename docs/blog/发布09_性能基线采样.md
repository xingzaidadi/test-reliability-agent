# 功能全绿 ≠ 性能没问题:p50 才 70ms,p95 却能翻一倍还带长尾

> 功能测试跑通了,但"这接口快不快"你心里有数吗?
> 这篇讲一个低成本高回报的能力:**复用已跑通的接口链路,顺手采个性能基线(p50/p95)**——
> 以及一个诚实的边界:这是**采样,不是压测**,别把两者搞混。

---

## 一、功能对了,不代表性能没问题

一个接口功能测试 PASS,只说明"结果对"。但它可能:
- p50 很好看(70ms),p95 却翻倍(160ms+),偶尔还有更长的尾巴
- 平均值把尾部风险藏起来了,你只看平均值就会漏掉

这些光看功能测试发现不了。**你需要一个性能基线**——知道它正常多快、尾部多慢、抖不抖,才能在它变慢时察觉。

---

## 二、几乎零成本:复用功能测试的链路

关键设计:**性能采样不重写请求,复用功能测试的 `run_case`(含 网关签名)**,只是同一个用例连发 N 次,统计分布。

```python
def run_perf_case(case, n=15):
    samples = [run_case(case)["duration_ms"] for _ in range(n)]  # 连发N次
    ordered = sorted(samples)
    return {
        "p50": percentile(ordered, 50),
        "p95": percentile(ordered, 95),
        "max": max(ordered),
    }
```

功能测试已经把"怎么真发出去"解决了,性能采样白捡这个能力——**加几十行,多一项能力。**

---

## 三、真实基线(15次采样)

某一次真实采样结果:

```
[PERF] TC_001 正向查询 x15 ... p50=72.9ms  p95=163.9ms  max=281.4ms  err=0
[PERF] TC_002 缺字段   x15 ... p50=66.0ms  p95=76.4ms   max=82.6ms   err=0
```

看 TC_001 那行——**p50 才 73ms,但 p95 飙到 164ms,max 破 280ms。** p95 比 p50 翻了一倍多。这个长尾,单跑一次功能测试根本发现不了,采样才暴露出来。**这就是基线的价值:让你看见平均值藏起来的尾部风险。**

> **诚实提醒:性能采样受网络波动影响,每次跑数字都不同**——我多次跑,p95 在 100~380ms 之间浮动过,max 偶发破秒。所以性能基线的正确用法不是"记住某个数字",而是**在稳定网络下多次采样,建立一个区间基线,后续用它当"变慢报警线"**。单次数字会骗你,趋势和区间才可信。

---

## 四、诚实的边界:这是采样,不是压测

我必须把这条边界说死,否则就是误导:

| | 性能基线采样(本文) | 压测 |
|---|---|---|
| 方式 | 串行连发 N 次 | 高并发打流量 |
| 目的 | 摸响应时间分布 | 找系统极限/瓶颈 |
| 对环境 | 几乎无压力 | 真加压 |

**它回答"这接口平时多快、尾部多慢",不回答"能扛多少并发"。** 真要压测,得上专门框架(JMeter/Gatling)。结果文件里我也写死了这句:`"note": "单请求串行采样,非并发压测"`——**不夸大成压测。**

## 五、复现

```bash
python tools/api-runner/api_execution_tool.py \
    --issue ISSUE-001 --perf --samples 15 --priority P0
```

## 六、诚实边界

- 采样非压测(上面说透了)。
- 串行采样受本机网络波动影响,基线应在稳定网络下多次取。

---

> **一句话**:功能测试证明"对不对",性能基线证明"快不快、尾部稳不稳"。复用已有链路,几十行就多一项能力——但记得诚实标注:这是采样,不是压测。
