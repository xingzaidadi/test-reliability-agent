# AI 写的测试用例,专业和业余差在哪?

> 让 AI 写测试用例,大家都会。但"写用例"和"设计测试"是两回事。
> 前者是把接口翻译成一堆请求;后者是从风险出发,想清楚"该测什么、为什么测、优先级怎么排"。
> 这篇讲:怎么让 AI 从可测性分析,走到有专业结构的测试设计——以及怎么判断它设计得到底专不专业。

---

## 一、"生成用例"和"测试设计"的鸿沟

你让 GPT "给这个接口写用例",它会给你一串:

```
- 正常查询
- 参数为空
- 参数超长
...
```

看着挺全,但这是**平铺的清单**,不是设计。真正的测试设计要回答三个问题:

1. **该测什么**(测试点从哪来——从风险和需求来,不是拍脑袋)
2. **为什么测**(每条用例对应什么风险)
3. **怎么排优先级**(P0/P1/P2,资源有限先测哪个)

这正是 ISTQB 和 该控制框架「双维度用例框架」在强调的:测试设计是**风险驱动的结构化活动**,不是用例的堆砌。

---

## 二、让测试设计"接着"可测性分析长出来

上一篇我们让 AI 做了可测性分析,拿到了 9 个测试点 + P0 风险。测试设计这一步,是把这些**结构化**成用例大纲。

关键是:**测试设计的输入,是上一步的可测性分析,不是接口本身。** 这形成一条链:

```
需求 → 可测性分析(测试点+风险) → 测试设计(结构化用例) → 用例生成 → 执行
```

用编排器的 DAG 把"分析→设计"串起来,前一步的产出喂给后一步:

```python
orch.submit(Task(id="REQ-ANALYZE", skill="analyze_requirement", ...))
orch.submit(Task(id="REQ-DESIGN",  skill="design_test",
                 depends_on=["REQ-ANALYZE"]))   # 依赖分析结果
# DAG 执行:分析完,结果自动注入设计任务
```

`design_test` 这个 skill 要求 AI 输出**带结构**的用例:

```python
Skill(name="design_test", prompt_template=(
    "根据可测性分析,把测试点设计成用例大纲。每条含:"
    "用例名、优先级(P0/P1/P2)、类型(正向/反向/边界/鉴权)、"
    "针对哪个接口、预期。\n可测性分析:\n{{analysis}}"
))
```

## 四、怎么判断它"专业"?看三个信号

不能光看"生成了很多条"就说专业。我看三个信号:

**信号1:有没有优先级判断。**
它把"合法查询""结果一致性""枚举校验"都标了 P0——因为这些是核心功能和高危风险。而不是所有用例一视同仁。**会排优先级,说明它理解了"什么更重要"。**

**信号2:有没有"想不到"的用例。**
"queryPrice 与 fetchPrice 结果一致性"这条——它不是针对单个接口的,而是发现了"这两个接口在业务上应该等价"这个隐含契约。**这种跨接口一致性用例,是资深测试才会主动加的。**

**信号3:枚举有没有正反都覆盖。**
它既有"合法枚举查正确价格(不串价)",又有"非法枚举校验拦截"——正反成对。**说明它理解了枚举字段的测试要点不只是"传对的",还有"传错的要被拦"。**

## 五、但"看着专业"还不够——这正是下一篇的引子

到这里,AI 设计出了一份**看起来很专业**的用例大纲。但——

> 看起来专业,和真的够充分,是两回事。

它设计了 N 条,可能该有 N+M 条。漏掉的那 M 条怎么办?"专业感"是主观的,**充分性必须是可度量的**。

这就是下一篇要解决的:不靠"感觉它挺全",而是**拿源码反推覆盖率**,让"够不够"变成一个数字。

## 七、诚实边界

- 测试设计目前产出的是"用例大纲"(结构化描述),转成可执行用例(带真实body/断言)还需下一环。
- LLM 有随机性:同一需求,这次设计9条,下次可能7条——**这恰恰是为什么需要下一篇的"可度量充分性"来兜底。**

---

> **一句话**:测试设计的专业度,体现在优先级、跨接口视野、正反覆盖上——AI 能做到。但"专业感"不能自证,得靠可度量的充分性来验证。
