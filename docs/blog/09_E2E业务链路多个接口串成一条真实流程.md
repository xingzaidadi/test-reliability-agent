# E2E 业务链路:把多个接口串成一条真实流程,让数据在步骤间流动

> 单接口测试只能证明"这个接口没坏"。但真实业务是**多个接口接力**完成的——
> 前一个接口的产出,是后一个的输入。这篇讲怎么让 AI 测试平台跑通**多步 E2E 业务链路**,以及关键的"上下文传递"。

---

## 一、为什么单接口测试不够

你把 pullPrice 测了、getPrice 也测了,单独都过。但真实场景是:

> 查到价格 → 用查到的编码去查数量 → 用数量去占用...

**每一步依赖上一步的产出。** 单接口各测各的,测不出"接力"环节的问题——比如上一步返回的 objectCode,下一步接口不认。E2E 就是测这个"链路是否连贯"。

---

## 二、E2E 的核心:上下文在步骤间传递

E2E 链路 = 有序的多步 + 步骤间传值。用 YAML 声明:

```yaml
steps:
  - step_id: E1
    name: 查询价格
    path: /x5/api/getPrice
    body: [{purchaseOrg: "2120", objectCode: "...", priceType: COST}]
    extract:                              # ← 从响应提取值
      chained_object_code: "$.body.data[0].objectCode"
  - step_id: E2
    name: 用上一步的objectCode再查
    path: /x5/api/getPrice
    body: [{objectCode: "{{chained_object_code}}", ...}]  # ← 用上一步的值
```

**关键机制**:E1 执行后,从响应里 extract 出 `chained_object_code`,注入到 E2 的 `{{}}` 占位——数据真实地从上一步流到下一步。任一步失败,整条链路中止。


注意 E1 那行末尾:**它提取出了 objectCode,E2 真的用这个值去查了。** 这不是两个独立请求,是一条**数据接力**的链路——这才是 E2E。

---

## 四、复用,不重造

E2E 执行器**没有重写请求逻辑**——它复用了 API 执行器的 `run_case`(含 X5 签名)。E2E 只多做一件事:**管理步骤顺序 + 上下文传递**。

```python
r = run_case(step, base_url, token, env_overrides=context)  # 复用API执行
if step.get("extract"):
    context[key] = json_path_get(r["response_body"], jpath) # 提取进上下文,供下一步
```

**复用是好工程**:签名、断言、请求这些"脏活"在 API 执行器里解决过一次,E2E 直接站在它肩上。

---

## 五、复现

```bash
python tools/api-runner/e2e_execution_tool.py --issue ISSUE-001
```

链路定义放 `e2e_flow.yaml`,换成你的多步业务流程即可。

---

## 六、诚实边界

- 目前是纯 API 多步链路(价格中心无 UI);含 UI 步骤的混合 E2E 需接入浏览器执行器。
- 上下文传递用极简 JSONPath(`$.a.b[0].c`),复杂提取需增强。

---

> **一句话**:E2E 的灵魂是"数据在步骤间流动"。单接口测"零件好不好",E2E 测"零件装起来转不转"——两者都要,后者更接近真实业务。
